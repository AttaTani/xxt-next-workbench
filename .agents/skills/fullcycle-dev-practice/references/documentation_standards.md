# 文档书写与治理规范 (Documentation Standards)

在工程研发全生命周期中，文档不是形式主义的代码附庸，而是**系统的设计蓝图、事实标准与维护合约**。

---

## 一、黄金四联文档体系 (The Golden Quad-Doc Suite)

任何非琐碎的功能演进、重大缺陷修复或重构，必须维护完整的四联文档：

```
┌─────────────────────────────────────────────────────────────┐
│ 1. PRD (产品需求规格书)                                      │
│    - 为什么要做？(Why)                                      │
│    - 具体的业务场景与交互体验边界？(What)                     │
└──────────────────────────────┬──────────────────────────────┘
                               │ 指导
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. TECH / RFC (技术设计方案与重构规格书)                     │
│    - 底层技术拓扑与 DOM/状态设计？(How)                     │
│    - 切片实施规划与风险回滚机制？                             │
└──────────────────────────────┬──────────────────────────────┘
                               │ 驱动
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. QA (缺陷排查分析与测试验收报告)                           │
│    - 发现了什么深层机制缺陷？(Root Cause)                    │
│    - 如何通过代码与自动化用例实现防回归？(Verification)       │
└──────────────────────────────┬──────────────────────────────┘
                               │ 沉淀
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. Handbook (系统设计与迭代维护手册)                         │
│    - 系统全局状态与数据流最新真值？(Single Source of Truth)  │
│    - 二次开发者如何接入与扩展？(Maintenance)                 │
└─────────────────────────────────────────────────────────────┘
```

## 二、各类文档的标准结构与撰写准则

### 2.1 产品需求规格书 (PRD) 标准结构
位于 `02_产品需求_PRD/`，文件命名如 `[Project]_PRD_[功能模块]_v[X.Y].md`。

1. **背景与设计初衷 (Context & Philosophy)**：阐述痛点背景、用户情绪或业务价值，严禁空泛词汇。
2. **场景与用户旅程 (User Journey)**：描述端到端的用户交互故事与动作闭环。
3. **核心功能矩阵 (Feature Matrix)**：
   - 基础体验层（P0）：核心阻塞功能
   - 交互增强层（P1）：手势、动效与抽屉
   - 边界防御层（P2）：误触兜底、降级机制
4. **交互体验与视觉基线 (Interaction & Visual Guidelines)**：明确工效学标准（如单手操作拇指热区、小屏 667px 极限高度防溢出）。
5. **验收标准 (Acceptance Criteria)**：可量化、可核验的检查条目。

### 2.2 技术方案设计 (TECH / RFC) 标准结构
位于 `03_技术方案_Architecture/`，文件命名如 `[Project]_TECH_[功能模块]_v[X.Y.Z].md`。

1. **架构现状与重构痛点 (Architecture Audit)**：当前代码的瓶颈点（如 DOM 过深、样式耦合、状态不一致）。
2. **核心技术选型 (Technical Decisions)**：技术方案选型依据，说明为什么选择方案 A 而非方案 B。
3. **分层技术实现 (Implementation Architecture)**：
   - 数据契约与状态机：定义全局 State、LocalStorage 结构与持久化机制。
   - DOM 拓扑减负：绘制组件层级树，精简嵌套深度。
   - CSS Token 体系：定义全局主题变量与响应式安全区适配。
4. **切片实施计划 (Slicing Roadmap)**：
   - `Slice 1`: 基础骨架与视口高度治理
   - `Slice 2`: 交互抽屉与状态绑定
   - `Slice 3`: 主题系统与样式解耦
   - `Slice 4`: 边缘加固与降级兜底
5. **风险与回滚方案 (Rollback Strategy)**：当切片引入未预见问题时的隔离与回退预案。

### 2.3 质量缺陷排查与验收报告 (QA) 标准结构
位于 `05_测试与验收_QA/`，文件命名如 `[Project]_QA_[缺陷/模块描述]_v[X.Y.Z].md`。

1. **缺陷背景与受影响环境 (Bug Context)**：机型、系统版本、浏览器环境、触发前置条件。
2. **缺陷表象 (Symptom)**：用户的直观遭遇（如“高度坍塌”、“抽屉无法上下滑动”）。
3. **根因机理深度剖析 (Root Cause Analysis)**：
   - 必须上升到**底层技术机制**层面（例如：为什么 Flex 子元素在未设置 `min-height: 0` 时会撑破容器？为什么移动端触控事件在未声明 `touch-action` 时会被默认浏览器行为拦截？）。
4. **修复方案与代码对比 (Fix Diff)**：精准对比修复前后的关键代码片段。
5. **自动化测试套件设计 (Automation Test Suite)**：展示编写的 Playwright / 单元测试脚本与核心断言逻辑。
6. **实机回归验收结论 (Verification Matrix)**：全用例测试结果（PASS / FAIL）矩阵。

### 2.4 系统设计与迭代维护手册 (Handbook) 标准结构
位于 `03_技术方案_Architecture/`，文件命名如 `[Project]_TECH_系统设计与迭代维护手册_v[X.Y.Z].md`。
作为整个软件资产的**终极真值载体**，每次重大版本升级（如 v2.8 -> v2.9）必须增量同步：

1. **系统全景架构 (System Overview)**：架构拓扑、技术基线、核心贡献者（Credits）。
2. **核心模块与全局状态流 (State & Data Flow)**：状态模型、事件发布订阅机制、本地持久化协议。
3. **视觉与交互规范 (Design Tokens)**：颜色、间距、圆角、层级 z-index 字典。
4. **二次开发与扩展指南 (Developer Guide)**：新卡包导入、新主题增加、原生平台构建操作 SOP。
5. **全生命周期变更日志 (Changelog)**：记录每一版本的演进历史与切片改造详情。

## 三、文档双轨编译与 Word 导出标准

为了兼顾代码版本管理（Git）与高管/非技术团队交付，推荐实施 **Markdown + Word 双轨制**：

1. **源文件为 Markdown (`.md`)**：存放在版本库，纯文本、轻量级、差异对比清晰；
2. **利用 `docx` 工具链编译成 Word (`.docx`)**：
   - 保持同名配对（如 `PRD_v1.0.md` 对应 `PRD_v1.0.md.docx`）；
   - 统一采用企业级专业排版模板（标题层级、首行缩进、深色高亮表格、代码块边框）；
   - 便于离线分发、打印及移动端排版阅览。
